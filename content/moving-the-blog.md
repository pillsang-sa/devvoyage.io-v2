Astro로 쓰던 블로그를 Next.js 16으로 다시 만들었습니다. 요구사항은 단순했습니다. **목록과 아티클, 두 개의 페이지**만 있으면 됩니다.

## Astro가 더 맞는 도구다

먼저 인정하고 시작하는 게 맞겠습니다. 이런 블로그에는 Astro가 더 어울립니다.

Astro는 페이지를 HTML로만 내보냅니다. 자바스크립트는 정말 필요한 곳에만 따로 심고, 이렇게 심은 조각을 아일랜드(island)라고 부릅니다. 정적인 바다 위에 인터랙션이 필요한 섬 몇 개만 띄우는 그림입니다. 목록과 아티클 두 페이지짜리 블로그의 요구사항과 정확히 일치합니다.

Next.js로 옮긴 이유는 기술적 우위가 아니라 **스택을 하나로 줄이고 싶어서**입니다. 업무에서 매일 Next.js를 쓰는데, 블로그를 고치려고 앉을 때마다 다른 프레임워크의 규칙을 다시 떠올려야 했습니다. 글을 쓰는 것보다 블로그를 손보는 데 마찰이 크면 결국 둘 다 안 하게 됩니다.

대신 치르는 값이 있습니다. 이 글이 실린 페이지를 열었을 때 브라우저가 실제로 내려받는 양을 재봤습니다.

| | 크기 | gzip |
| --- | --- | --- |
| HTML | 99KB | 20KB |
| 클라이언트 JS | 620KB | **185KB** |

이 페이지에서 자바스크립트가 필요한 곳은 헤더의 테마 토글 버튼과 코드 블록의 복사 버튼, 두 군데뿐입니다. Next.js에서는 브라우저에서도 돌아야 하는 파일 맨 위에 `'use client'`라고 적어 표시하는데, 저장소를 통틀어 그게 붙은 파일이 그 두 버튼입니다.

나머지는 전부 빌드할 때 미리 만들어 둔 정적 HTML입니다. 그런데 페이지에 브라우저에서 동작하는 부분이 **하나라도** 있으면, Next.js는 React 본체와 페이지 전환을 담당하는 코드까지 통째로 함께 내려보냅니다. 버튼 두 개에 185KB인 셈입니다. 복사 버튼을 나중에 더했을 때 늘어난 건 1KB 남짓이었으니, 이 값의 거의 전부는 버튼이 아니라 React 본체입니다.

Astro였다면 0에 가까웠을 값입니다. 실제로 테마를 처음 적용하는 일은 이미 `<head>` 안의 인라인 스크립트 몇 줄로 처리하고 있으니, 두 버튼도 같은 방식으로 못 만들 이유가 없습니다.

그래도 저는 이 거래가 남는 장사라고 봅니다. 185KB는 방문자가 한 번 받아두면 브라우저가 캐시해 두고 다시 받지 않습니다(여기엔 단서가 붙는데, 뒤에서 다룹니다). 반면 프레임워크를 오갈 때 드는 인지 비용은 글을 쓸 때마다 반복해서 내야 하는 값입니다. 다만 그건 **제 사정이지 기술적 근거는 아닙니다.** 블로그 하나만 새로 만드는 상황이라면 저는 Astro를 권하겠습니다.

## Astro가 해주던 일을 직접 하기

스택을 하나로 줄이고 치른 값은 185KB만이 아니었습니다. Astro에서는 프레임워크가 알아서 해주던 일을 Next.js에서는 직접 조립해야 했고, 그 과정에서 함정을 두 개 만났습니다.

### 마크다운을 HTML로 바꾸기

Astro는 마크다운을 기본으로 다룹니다. `.md` 파일을 HTML로 바꾸는 것도, 코드 블록에 색을 입히는 것도 설정 없이 됩니다. 코드 하이라이터도 처음부터 Shiki가 들어 있습니다.

Next.js에는 이런 기능이 없습니다. MDX 파일을 페이지로 쓰는 공식 방법은 있지만, 폴더에 모아둔 글을 읽어서 렌더하는 일은 직접 해야 합니다. 그래서 본문은 `react-markdown`으로 렌더링하고, 코드 하이라이팅은 `rehype-pretty-code` 플러그인에 맡겼습니다. 여기서 첫 번째 함정을 만났습니다.

`react-markdown`이 기본으로 제공하는 `Markdown` 컴포넌트는 변환을 **동기로** 실행합니다. 동기는 결과가 나올 때까지 그 자리에서 기다리는 방식입니다. 그런데 `rehype-pretty-code`는 내부적으로 Shiki라는 하이라이터를 씁니다. Shiki는 VS Code와 같은 엔진으로 색을 입히는데, 그러려면 문법 정의와 테마 파일을 먼저 읽어와야 합니다. 파일을 읽어오는 일은 시간이 걸리므로 **비동기**입니다. 준비되면 알려달라고 해두고 일단 넘어가는 방식입니다.

기다릴 생각이 없는 쪽에 기다려야 하는 일을 밀어 넣은 셈이라, 그대로 조합하면 이런 에러가 납니다.

```text
Error: `runSync` finished async. Use `run` instead
```

"동기로 돌리라고 했는데 중간에 비동기 작업이 끼어들었다"는 뜻입니다.

해결책은 v10이 제공하는 `MarkdownAsync`입니다. 이름 그대로 기다릴 줄 아는 버전이고, 서버에서만 실행되므로 브라우저로 내려가는 코드도 늘지 않습니다.

```tsx
import { MarkdownAsync } from "react-markdown";
import rehypePrettyCode from "rehype-pretty-code";
import remarkGfm from "remark-gfm";

export function Markdown({ children }: { children: string }) {
  return (
    <MarkdownAsync
      remarkPlugins={[remarkGfm]}
      rehypePlugins={[[rehypePrettyCode, { theme: "github-dark-dimmed" }]]}
    >
      {children}
    </MarkdownAsync>
  );
}
```

Astro에서는 볼 일이 없는 에러입니다. 마크다운 변환을 처음부터 기다리는 방식으로 돌리기 때문입니다.

### 날짜에 숨어 있던 함정

두 번째 함정은 더 조용했습니다.

글 맨 위의 제목과 날짜 같은 정보(frontmatter)도 Astro에서는 콘텐츠 컬렉션이 읽어 주고, 스키마에 타입을 적어두면 빌드할 때 검사까지 해줍니다. Next.js에서는 읽는 일부터 직접 해야 해서 `gray-matter`라는 라이브러리를 썼고, 이 라이브러리는 frontmatter를 YAML로 읽습니다. 그런데 YAML은 따옴표 없는 `2026-08-04`를 날짜로 알아보고, **문자열이 아니라 JS `Date` 객체로** 바꿔서 돌려줍니다. 편의 기능이지만 여기서는 반갑지 않습니다. 어떤 글은 문자열, 어떤 글은 `Date`가 되면 정렬하고 출력하는 코드가 두 경우를 다 신경 써야 합니다.

그래서 파일을 읽어들이는 지점에서 한 번 문자열로 통일해 둡니다. 이후 코드는 항상 `"2026-08-04"` 형태만 상대하면 됩니다.

```ts
function toDateString(value: unknown): string {
  if (value instanceof Date) {
    return value.toISOString().slice(0, 10);
  }
  // ...
}
```

화면에 찍을 때는 로케일과 타임존을 코드에 직접 못 박았습니다. 그러지 않으면 기준이 빌드하는 컴퓨터의 설정을 따라갑니다. 제 노트북에서 빌드할 때와 GitHub 서버에서 빌드할 때 날짜가 하루씩 어긋날 수 있다는 뜻입니다. 고정해 두면 어디서 빌드하든 같은 결과가 나옵니다.

## GitHub Pages에 올린다는 것

배포는 GitHub Pages로 합니다. `main`에 푸시하면 GitHub Actions가 빌드해서 결과 파일을 올립니다. 비용은 0원이고 관리할 서버도 없습니다.

대신 GitHub Pages는 **파일을 돌려주기만 하는 곳**입니다. 앞단에 CDN이 있지만, 그 뒤에서 제 코드를 실행해 줄 곳이 없습니다. Vercel이나 EC2에 올린 Next.js는 요청이 올 때마다 서버에서 코드를 돌릴 수 있지만, 여기서는 모든 페이지가 빌드할 때 HTML로 만들어져 있어야 합니다. 그래서 `next.config.ts`에 `output: "export"`를 켭니다.

이 한 줄로 잃는 것들입니다.

| 잃는 것 | 이 블로그에서는 |
| --- | --- |
| 요청마다 페이지 생성(SSR), 주기적 재생성(ISR) | 모든 페이지를 빌드할 때 생성하고, 글이 바뀌면 다시 배포 |
| API 라우트, Server Actions | 쓸 일이 없음 |
| 이미지 최적화(`next/image`) | 빌드할 때 크기를 읽어 넣고, 이미지는 AVIF로 미리 변환 |
| 응답 헤더·리다이렉트 설정 | 설정할 방법이 없음 |

앞의 셋은 블로그에 필요 없는 기능이라 잃어도 괜찮았습니다. 아픈 건 마지막 줄, 그중에서도 **캐시 헤더**입니다.

Next.js는 빌드할 때 자바스크립트 파일 이름에 내용의 해시를 붙입니다. 내용이 바뀌면 이름도 바뀌므로, 원래는 "이 파일은 영원히 캐시해도 된다"(`immutable`)고 알려주는 게 정석입니다. 그런데 GitHub Pages에서는 헤더를 고를 수 없고, 모든 파일이 똑같이 10분짜리 캐시를 받습니다.

```text
cache-control: max-age=600
etag: "6ae19f67-449f"
```

10분이 지나면 브라우저는 파일이 바뀌었는지 다시 묻습니다. 그대로라면 본문 없이 "그대로"라는 답만 오니 다시 받지는 않습니다. 문제는 그 판단 기준인 `etag`입니다. 앞부분 `6ae19f67`은 파일이 올라간 시각이고, 뒷부분은 파일 크기입니다. 그래서 **배포할 때마다 모든 파일의 etag가 바뀝니다.** 오타 하나만 고쳐 배포해도, 재방문자는 내용이 그대로인 185KB를 처음부터 다시 받습니다.

앞에서 "한 번 받아두면 다시 받지 않는다"고 한 말은 반만 맞습니다. 다음 배포 전까지만입니다.

그 밖에도 몇 가지 차이가 있습니다.

- **주소 끝 슬래시**: `/blog/foo`로 들어오면 GitHub Pages가 `/blog/foo/`로 돌려보냅니다(301). 그래서 `trailingSlash: true`로 빌드하고, canonical 주소와 사이트맵도 전부 슬래시로 끝나게 맞췄습니다. 그러지 않으면 검색엔진에 알려준 주소마다 리다이렉트를 한 번씩 거칩니다.
- **미리보기 배포 없음**: Vercel처럼 PR마다 미리보기 주소가 생기지 않습니다. 확인은 로컬에서 빌드해서 합니다.

정리하면, 서버를 공짜로 없앤 대가로 캐시 제어권을 내준 거래입니다. 배포가 드문 개인 블로그에서는 남는 장사입니다. 하지만 자주 배포하고 재방문자가 많은 사이트라면, Vercel이나 Cloudflare Pages처럼 헤더를 설정할 수 있는 곳이 낫습니다.

## 옮기면서 알게 된 것

이전 블로그는 Astro + MDX였습니다. MDX는 마크다운 안에 컴포넌트를 섞어 쓸 수 있는 형식인데, 한 파일에 글과 코드 블록과 JSX가 뒤엉키는 게 지저분해 보였습니다. 그래서 **코드 예제만 따로 뺐습니다.** 예제를 `.ts` 파일에 담아두고, 본문에서는 import해서 렌더하는 방식이었습니다.

```ts
// snippets/dockerfile.ts
export const dockerfileSnippet = `
RUN \
  if [ -f yarn.lock ]; then yarn --frozen-lockfile; \
  else echo "Lockfile not found." && exit 1; \
  fi
`;
```

```mdx
import { dockerfileSnippet } from "./snippets/dockerfile";

<CodeBlock code={dockerfileSnippet} lang="dockerfile" />
```

정리한 기분이 들었습니다. 그런데 이 분리가 문제의 원인이었습니다.

### 밖으로 빼는 순간 성격이 바뀐다

코드를 본문에 두면 그건 **글**입니다. 마크다운이 읽고 화면에 그대로 내보냅니다.

코드를 `.ts` 파일로 빼면 그건 **프로그램의 값**이 됩니다. 화면에 나오기 전에 자바스크립트가 먼저 읽습니다. 눈에는 똑같은 코드가 보이지만, 사이에 파서가 하나 더 낀 것입니다.

그리고 자바스크립트에게 백슬래시(`\`)는 평범한 글자가 아닙니다. "다음 글자는 특별하게 읽어라"는 신호입니다. 그래서 자바스크립트는 문자열을 읽으면서 백슬래시를 자기 몫으로 가져가 버립니다. 제가 파일에 쓴 것과 독자가 화면에서 보는 것이 달라집니다.

| 원래 쓴 것 | 자바스크립트의 해석 | 페이지에 나간 것 |
| --- | --- | --- |
| `\d`, `\[` | 모르는 조합이라 백슬래시만 버림 | `d`, `[` |
| `\"` | 따옴표를 감싸주는 표시 | `"` |
| `\n` | 줄바꿈 문자 | 실제 줄바꿈 |
| `RUN \` + 줄바꿈 | 다음 줄을 잇는 표시 | 한 줄로 붙음 |

옮겨온 7편 중 6편의 코드가 이렇게 손상돼 있었습니다.

**정규식은 의미가 바뀌었습니다.** 숫자 하나를 뜻하는 `\d`가 `d`가 되면, 숫자를 요구하던 조건이 알파벳 d를 요구하는 조건으로 변합니다. 문법은 멀쩡해 보이는데 동작만 다릅니다.

**`package.json` 예제는 붙여넣으면 에러가 났습니다.** JSON에서 문자열 안의 따옴표는 `\"`로 적어야 하는데, 백슬래시가 사라지면서 따옴표가 엉뚱한 자리에서 문자열을 끝내버렸습니다.

**여러 줄짜리 셸 명령은 한 줄로 뭉개졌습니다.** 위 예제의 줄 끝 백슬래시는 "이 명령은 다음 줄에 이어진다"는 표시인데, 자바스크립트가 그걸 먼저 가져가면서 여섯 줄이 한 줄로 붙었습니다.

### 아무도 알려주지 않는다

가장 나쁜 점은 **에러가 안 난다는 것**이었습니다. 백슬래시가 사라진 결과물도 문자열로서는 완벽히 유효합니다. 타입 체크도 통과하고, 빌드도 성공하고, 페이지도 잘 뜹니다. 발견하려면 올라간 글을 하나하나 열어 원본과 눈으로 대조하는 수밖에 없습니다. 6편이 그 상태로 방치돼 있었던 이유입니다.

물론 그 구조를 유지한 채로도 고칠 수는 있었습니다. `String.raw`를 붙이거나 백슬래시를 전부 두 개씩 쓰면 됩니다. 하지만 그건 **예제를 쓸 때마다 사람이 기억해야 하는 규칙**이고, 잊어버려도 아무도 알려주지 않습니다. 사람의 기억력에 정확성을 맡기는 설계입니다.

### 해결은 다시 안으로 넣는 것

지금은 코드가 본문 안 마크다운 펜스에 그냥 있습니다. 여는 펜스와 닫는 펜스 사이는 있는 그대로의 텍스트일 뿐이라, 자바스크립트를 거치지 않고 화면에 나옵니다.

| | 옛 방식 | 지금 |
| --- | --- | --- |
| 코드가 있는 곳 | `.ts` 파일, import | `.md` 파일, 펜스 안 |
| 거치는 파서 | 자바스크립트 → MDX → HTML | 마크다운 → HTML |
| `\` 다룰 때 | 두 개씩 쓰거나 `String.raw` | 그냥 씀 |
| 틀렸을 때 | 에러 없음, 조용히 깨짐 | 틀릴 것이 없음 |

설치한 라이브러리도, 켠 옵션도, 붙인 플래그도 없습니다. **파서 한 겹을 없앤 게 전부입니다.**

파일이 지저분해 보여서 정리하려던 리팩터링이 원인이었다는 게 이 일의 교훈입니다. 코드를 밖으로 빼면 파일은 깔끔해지지만, 그 코드는 글이기를 그만두고 프로그램의 일부가 됩니다. 보여주기만 할 텍스트라면 남에게 해석시키지 말고 본문에 그냥 두는 편이 낫습니다.
